# Internationalization (next-intl)

This dashboard serves **English (`en`)** and **Arabic (`ar`)** from one codebase.

## Architecture

| Piece | Path | Role |
|---|---|---|
| Locales | `src/i18n/routing.ts` | `en` / `ar`, default `en` |
| Direction helpers | `src/lib/i18n/direction.ts` (re-exported from `src/i18n/config.ts`) | `getDirection`, `isRtl` |
| Navigation APIs | `src/i18n/navigation.ts` | Locale-aware `Link`, `usePathname`; `useRouter` is wrapped with the top loader |
| Action translations | `src/i18n/get-action-translations.ts` | Resolve catalogs in server actions without `getLocale()` |
| Request config | `src/i18n/request.ts` | Loads `messages/{locale}.json` |
| Proxy | `src/proxy.ts` | Locale detection + session refresh (Next.js 16) |
| Catalogs | `messages/en.json`, `messages/ar.json` | All UI copy |

Routes live under `src/app/[locale]/…` → `/en/…` and `/ar/…`.

`apiClient` sends `Accept-Language` from `getRequestLocale()` so backend messages match the current locale.

## Reusable patterns

### Prefer these over raw Next APIs

```tsx
import { AppLink } from "@/components/shared/navigation/AppLink";
import { usePathname, useRouter } from "@/i18n/navigation";
```

`useRouter()` starts the top loader on `push` / `replace`.

### Server vs client translations

```tsx
// Server Component
import { getTranslations, setRequestLocale } from "next-intl/server";
const { locale } = await params;
setRequestLocale(locale);
const t = await getTranslations({ locale, namespace: "Dashboard" });

// Client Component
import { useTranslations, useLocale } from "next-intl";
const t = useTranslations("Filters");

// Server action
import { getActionTranslations } from "@/i18n/get-action-translations";
const t = await getActionTranslations(locale, "Auth.loginForm");
```

### Navigation config stays language-agnostic

`src/config/navigation.ts` stores `id` + `titleKey` (never translated titles).  
Resolve titles with `useTranslatedNavigation()` in client shell components.

### RTL / LTR

- `lang` + `dir` are set on `<html>` in `[locale]/layout.tsx`
- Sidebar `side` flips via `useIsRtl()`
- Prefer logical Tailwind: `ms` / `me` / `ps` / `pe` / `start` / `end` / `text-start`
- Directional icons: `className="rtl:rotate-180"`
- LTR islands for email, price, passwords: `dir="ltr"`

### Locale switcher

`LocaleSwitcher` preserves the current pathname while swapping `/en` ↔ `/ar`.

## Shared namespaces

Add keys to **both** catalogs:

- `Metadata.appName` — title template (`{appName} - %s`)
- `Crud` — confirm/cancel/save/errors for the forms kit
- `Common.error` / `Common.forbidden` / `Common.notFound` / `Common.breadcrumb`
- `Auth.loginForm` — login fields, validation, submitting
- `Table` — empty + selection chrome

## Adding a new page

1. Add the route under `src/app/[locale]/(main)/…`
2. Add keys to **both** `messages/en.json` and `messages/ar.json`
3. Wire `getTranslations` / `useTranslations`
4. If it appears in the sidebar, add an entry with `titleKey` in `config/navigation.ts` and matching `Nav.*` keys

Shared table chrome (`empty`, `selection.*`) lives in the `Table` namespace and is used by `DataTable` / `DataTableBulkBar`. Entity column headers and bulk-delete copy belong in the entity namespace. See [Table](./features/table.md#i18n).
